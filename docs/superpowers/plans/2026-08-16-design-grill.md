```markdown
# Design Grill

## Overview

Use this skill to clarify game-design work before drafting. Treat the request as a decision tree, separate facts from guesses and user-owned decisions, ask the current frontier, and wait for shared-understanding confirmation before producing a full design artifact.

MarkItDown, when present in a project, is only an ingestion adapter for converting source files into Markdown. Do not treat it as the agent runtime, knowledge base, design framework, or numeric solver.

## Required Flow

1. Identify the design domain: numeric, system, level, narrative, or mixed.
2. Gather verifiable facts from provided text, files, local project context, or cited source material.
3. Separate the working state into Confirmed Facts, Inferences, User Decisions, and Open Questions.
4. Model the request as a decision tree and identify the current frontier: questions with no unresolved dependencies.
5. Ask the frontier question or questions with a recommendation and reason.
6. Recompute the decision tree after the user answers.
7. Restate the shared understanding when direction-changing uncertainty is closed.
8. Wait for user confirmation before drafting a full PRD, numeric plan, system spec, level design, or narrative design.

## Question Rules

- Investigate facts yourself when they can be found from available context.
- Ask the user for product, business, creative, priority, or taste decisions.
- Prefer one question at a time for complex design work.
- Ask two or three questions only when they are simple, independent, and answerable without deep context switching.
- Attach a recommended option to each question.
- Label uncertainty. Do not write guesses as confirmed facts.

## Domain Routing

Read `references/domain-adapters.md` when the request involves game-specific design domains, including numeric design, system design, level design, narrative design, economy, progression, balancing, rewards, guilds, events, onboarding, missions, quests, or story.

Use adapters as checks layered on top of the universal flow. Adapters do not replace the design tree, confirmation gate, or fact/decision separation.

## Output And Persistence

Read `references/persistence-output.md` before preparing a structured response, writing a persistent artifact, or deciding whether a user request authorizes file writes.

Default to session-only work. Write files only when the user explicitly asks to save, generate, record, persist, or write an artifact. If persistence is requested but the target is unclear, ask for the artifact type or path before writing.

## Stop Conditions

Stop before full design output when any unresolved decision can change the direction of the design.

Proceed to drafting only when:

- the goal, audience, constraints, and success criteria are clear enough for the requested artifact;
- no open question can overturn the proposed direction;
- you can restate the shared understanding in one or two sentences;
- the user confirms that understanding.

## Common Mistakes

| Mistake | Correction |
| --- | --- |
| Writing the full PRD immediately | Ask the current decision frontier first |
| Treating inferred player goals as facts | Put them under Inferences with basis |
| Asking users for facts available in files | Inspect available context first |
| Letting a domain adapter own the workflow | Keep the universal design tree as the driver |
| Saving documents by default | Save only after explicit user intent |
| Copying generic advice over project rules | Current project sources and user-confirmed rules win |
```

```markdown
# Domain Adapters

Use this reference to add game-domain checks after the universal decision-tree workflow is active. Adapters identify missing constraints and frontier questions. They do not authorize drafting before user confirmation.

## Numeric Design

Use for economy, progression, growth, rewards, values, probability, balancing, difficulty, resource pacing, shops, drops, crafting, stamina, or paid/free assumptions.

Check these dimensions:

- target player segment and design period
- daily activity and retention assumption
- core resource sources and sinks
- milestone rhythm and growth curve
- expected value, variance, floor, ceiling, guarantee, and pity rules
- free/paid assumptions and sensitivity boundaries
- spreadsheet, config, or simulation output requested by the user

Common frontier questions:

- "这个数值节奏主要服务哪类玩家？推荐先按零付费/高活跃玩家做基线，因为这样能先保证主线体验不被付费假设污染。"
- "设计周期是 D1-D7、D1-D14 还是更长？推荐先锁 D1-D7，因为早期养成节奏最容易影响留存。"
- "你希望我先产出节奏框架、资源账本，还是可落表的数值草案？推荐先产出节奏框架，再进账本。"

Do not:

- invent source/sink quantities when the user has not provided them;
- present config-ready numbers as confirmed without source or user approval;
- mix planning assumptions with runtime-verified behavior.

## System Design

Use for gameplay systems, feature PRDs, guilds, social systems, events, unlocks, progression systems, mechanics, missions, shops, tasks, or live-ops systems.

Check these dimensions:

- core loop
- entry and unlock conditions
- actor roles and permissions
- states and transitions
- reward boundary and economy impact
- failure, abuse, edge, and rollback paths
- dependencies on config, UI, server, analytics, operations, or content

Common frontier questions:

- "这个系统的核心循环是个人成长、多人协作，还是竞争排行？推荐先锁核心循环，因为它决定奖励、门槛和社交压力。"
- "这是长期常驻系统还是限时活动？推荐先确认生命周期，因为常驻系统更需要成长和反滥用边界。"
- "你想先要玩法框架还是 AI 可执行 PRD？推荐先做玩法框架，确认后再写 PRD。"

Do not:

- write a full PRD before the core loop and success criteria are confirmed;
- define reward amounts before reward boundary and economy impact are known;
- ignore abuse or rollback paths for social and competitive systems.

## Level Design

Use for stages, maps, missions, encounters, onboarding, tutorials, difficulty pacing, combat beats, or content progression.

Check these dimensions:

- teaching objective
- player entry state and required knowledge
- spatial, encounter, or mission rhythm
- difficulty ramp and recovery path
- readable feedback and failure reason
- dependency on available mechanics, monsters, terrain, rewards, and content budget

Common frontier questions:

- "这个关卡主要教学、检验、卡点还是情绪释放？推荐先锁教学/检验目标，因为它决定难度和节奏。"
- "玩家进入时已经掌握哪些机制？推荐只引入一个新负担，降低早期认知成本。"
- "你希望输出关卡节奏表、遭遇草案，还是完整关卡文档？推荐先输出节奏表。"

Do not:

- add mechanics without confirming the player has learned prerequisites;
- create difficulty spikes without recovery or readability;
- treat narrative atmosphere as a substitute for playable objective clarity.

## Narrative Design

Use for story, character arcs, dialogue, quests, world-building, plot structure, emotional beats, lore, or information reveal order.

Check these dimensions:

- player role and agency
- character motivation
- conflict and stakes
- information reveal order
- emotional beat and pacing
- continuity, localization, and tone constraints

Common frontier questions:

- "这段剧情主要承担世界观解释、角色塑造、任务动机，还是情绪爆点？推荐先锁功能，因为它决定信息量和节奏。"
- "玩家在剧情里是旁观、选择、执行，还是改变结果？推荐先确认玩家能动性，因为它决定任务结构。"
- "你想先要剧情骨架、任务链，还是可直接进文档的对白草案？推荐先要剧情骨架。"

Do not:

- write final dialogue before角色目标、冲突和语气 are confirmed;
- over-explain lore before the player's immediate motivation is clear;
- break established project continuity without flagging the conflict.

## Mixed-Domain Requests

When a request spans multiple domains, choose one primary adapter and list the secondary checks.

Recommended ordering:

1. System design first when the core loop is unclear.
2. Numeric design first when the loop is known and the main risk is balance or pacing.
3. Level design first when the feature is experienced through staged content.
4. Narrative design first when player motivation, character intent, or information reveal is the main uncertainty.
```
